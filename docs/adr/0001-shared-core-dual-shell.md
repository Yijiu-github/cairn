# ADR-0001: 采用「共享核心 + 双外壳」而非 Web-only

- **状态**：🟢 Accepted
- **日期**：2026-05-13
- **决策者**：项目主理
- **关联**：[`../design/设计文档V0.1.0.md#6-产品形态共享核心--双外壳--双运行模式`](../design/设计文档V0.1.0.md)

---

## 背景

v0.3 之前默认前提是「先做 Web 工作台，桌面端以后再说」。

但产品的真实定位是：

- 面向个人开发者与小技术团队
- 本地优先、自托管
- Windows 与 macOS 桌面版近期上线

如果继续按 Web-only 设计，桌面端会变成"补洞式移植"，后续会在 runtime 生命周期、子进程、文件系统、更新分发、权限模型等多处重构。

## 决策

**Desktop 与 Web 都是一等外壳，必须共享同一套协作核心。**

具体地：

1. 桌面端（Windows + macOS Apple Silicon）和 Web 端都基于同一 Workspace Core
2. 两个外壳共享：领域模型、API 契约、状态机定义、运行详情结构、UI 组件层业务逻辑
3. 允许分开的部分：桌面系统能力桥接、自动更新与安装器、本地文件与系统菜单、浏览器登录与远程鉴权流程
4. 不是三套产品：本地桌面版、远程 Web 版、未来团队版三者的差异只体现在部署方式、存储后端、权限协作能力上，不允许协作核心语义分叉

## 后果

### 好的

- 桌面端从一开始就受重视，避免后期"补洞式移植"
- 核心语义只有一套，长期维护成本低
- 用户在桌面 ↔ Web 之间切换无感
- 远程工作区模式天然支持（同一 core 部署到 Linux server 即可）

### 坏的

- 第一版技术选型必须同时满足桌面与 Web 双方约束（影响主语言、框架等决策——见 ADR-0002 / 0003）
- 短期内研发投入比"只做 Web"更大
- 需要更严的契约管理避免双端分裂

### 中性的

- 必须在 Release 1 中明确"先交付哪一端的哪一部分"（见 [`../product/roadmap.md`](../product/roadmap.md)）

## 备选方案

- **方案 A：Web-only，桌面延后**  
  优点：MVP 快；缺点：技术栈选型被早期假设锁死，桌面端注定是二等公民。
- **方案 B：桌面-only，先不做 Web**  
  优点：聚焦；缺点：失去远程团队场景，且 Web 控制台是用户合理预期。
- **方案 C：桌面与 Web 各自独立后端**  
  优点：各自最优；缺点：两套语义、两套数据模型、两倍工程量与运维量——产品长期会分裂。
