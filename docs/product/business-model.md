## 1. 模式候选

### 模式 A：完全开源（MIT / Apache-2.0）

#### 形态
- 仓库公开
- 任何人可自由使用、修改、再分发，包括商业
- 不提供官方 SaaS，只提供软件本体

#### 优点
- 信任建立最快
- 社区贡献最积极
- 对"自托管偏执用户"最友好
- 维护者零商业义务

#### 缺点
- 没有商业收入路径（除捐赠 / 赞助）
- 容易被大厂"借走"并提供托管服务而你没收益
- 签名证书 / 服务器 / 时间投入难以可持续

#### 适合
- 把它作为个人作品 / 简历项目 / 长期 hobby
- 不打算从中谋生

---

### 模式 B：开源 + 增值（Open Core）

#### 形态
- 核心开源（MIT / Apache-2.0）
- 团队 / 企业增值功能闭源（如：SSO、审计、共享 workspace、官方支持）
- 提供官方托管服务（可选）

#### 优点
- 兼顾信任与变现
- 个人用户全免费，扩大基础
- 团队功能可付费

#### 缺点
- "Core 与 Enterprise"边界容易吵架
- 维护两套代码 / 两套体验
- 部分用户会感到"被分级"

#### 适合
- 当前最常见的开发者工具商业模式（如 GitLab、Sentry、PostHog）

---

### 模式 C：BUSL-1.1（Business Source License）

#### 形态
- 源码公开可读、可修改、可个人使用
- 商业用途有限制（如禁止提供托管服务）
- N 年后（典型 4 年）自动回落到 Apache-2.0

#### 优点
- 保护自己不被大厂托管"借走"
- 仍然源码公开，社区可参与
- N 年后社区获得完全自由

#### 缺点
- 不算"真正开源"（OSI 不认证）
- 部分用户拒绝接受 BUSL
- 配套商业条款需要律师

#### 适合
- 想长期商业化 + 保留社区信任的中间路线（如 HashiCorp、Sentry 后期、CockroachDB）

---

### 模式 D：完全闭源 + 商业化

#### 形态
- 源码不公开
- 通过付费授权 / 订阅获取使用权
- 提供官方支持

#### 优点
- 商业边界清晰
- 收入路径直接

#### 缺点
- 在"本地优先 / 自托管偏执用户"群体里很难建立信任
- 与 Cairn 的核心价值（数据归用户、可迁移、可审计）有张力
- 对个人项目而言营销成本极高

#### 适合
- 已有客户基础和销售能力的团队，**不推荐个人项目**

---

## 2. 我对个人项目的初步推荐

### 推荐路径：**开源 Apache-2.0 + 远期可选模式 B**

理由：

1. **当前你是一个人 / 小团队**，没有销售带宽，模式 D 不现实
2. **本地优先 + 自托管**的卖点要求源码可读可审计，BUSL 已经会让一部分目标用户却步
3. **Apache-2.0** 比 MIT 多了专利条款，企业更敢用
4. **R1 / R2 阶段先建用户基础和声誉**，R3 之后若团队版有明显需求，再考虑 Open Core（模式 B）
5. **签名证书 / 服务器** 等成本可通过 **GitHub Sponsors / OpenCollective / 企业级支持** 覆盖

### 不推荐的路径

- ❌ 一开始就 BUSL：会损失早期社区信任
- ❌ 一开始就完全闭源：跟产品价值观相悖
- ❌ 永远不商业化：长期不可持续，作者最终会放弃

## 3. 配套决策

### 3.1 License 文件

待拍板。当前 `LICENSE` 文件是占位（TBD）。决定后：

- 提交标准 LICENSE 文本
- 在 README、ADR、CHANGELOG 中同步

### 3.2 商标 / 项目名

- "Cairn" 作为项目名：考虑是否注册商标（如商业化）
- 若开源 + 增值模式，建议保留对项目名的控制（避免他人拿名字做托管服务）

### 3.3 Telemetry

详见 [`../design/telemetry-and-privacy.md`](../design/telemetry-and-privacy.md)。

无论选哪种模式：

- **默认只收集启动 + 崩溃 + 匿名使用计数**
- **永远不上报业务内容**
- **永远可一键关闭**

### 3.4 收入路径（如商业化）

候选：

- GitHub Sponsors / OpenCollective（自愿赞助）
- 团队版订阅（如选模式 B）
- 官方托管 / 远程模式服务（如选模式 B）
- 企业支持合同
- 培训 / 顾问
